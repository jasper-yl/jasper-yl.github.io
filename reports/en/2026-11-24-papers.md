### [How Feedback-Free Self-Evolution Reshapes Agent Skills](https://arxiv.org/abs/2611.25534)
- Heat: HF 👍4 (4 days on the list, +4); repo [LitaoGuo/How-Self-Evolution-Reshapes-Skills](https://github.com/LitaoGuo/How-Self-Evolution-Reshapes-Skills) ⭐3.
- Problem: when a model repeatedly rewrites expert-written skill documents with no feedback, do the skills get better or worse?
- Method: the model rewrites expert skills round after round, with no tasks, runs or judges, then an agent is run with the rewritten skills. Rewriting pulls skills toward the model's own priors, and the knowledge outside those priors is lost first. Putting that knowledge back recovers most of the loss. The authors propose SkillDiff, which marks this knowledge in place without changing the skill text.
- Result: every tested model gets worse on every benchmark, losing 15 points on average on SkillsBench after 30 rounds. SkillDiff improves scores by 4.8 points on average. It is the only Context paper in this batch with upvotes.

### [Experience Rot: Experienced Agents Fail Where Novices Succeed](https://arxiv.org/abs/2611.20922)
- Problem: agents accumulate experience through conversation history, memory files, retrieval notes and skills. What happens when a tool (MCP) is silently changed?
- Method: compare experienced and novice agents after an MCP tool definition changes silently. The experienced agents copy earlier calls without checking the current interface, and still report success.
- Result: after the change, experienced agents fail most tasks while novices mostly succeed. This appears in every memory form tested and gets worse with more experience. Simple fixes help little: telling the agent the tool was "updated" does almost nothing, and pointing it to the docs fails when the docs don't state the answer. This is the sharpest conclusion in the batch and the best headline candidate.

### [Instant Weight-Space Consolidation for Long-Term Memory in LLMs (CLAM)](https://arxiv.org/abs/2611.20759)
- Problem: text-based agent memory extraction is error-prone and the errors accumulate, build cost grows with the conversation, and the model itself never evolves.
- Method: a recurrent hypernetwork compiles the stream of session activations into a low-rank adapter in one forward pass, with no gradient steps and no LLM generation calls. A fixed-size gated latent state accumulates across sessions, and an episodic buffer adds back verbatim detail.
- Result: on LoCoMo and LongMemEval-S with three 2–7B open models, it beats all agentic baselines by 1–45 points and gradient-based parametric methods by 10–45 points. Memory construction is 3–151× faster than extraction-based systems. The two channels complement each other: when the buffer misses the evidence, the adapter adds 12–15 points, and it still adds 4–5 points even with an oracle buffer.

### [LEDGER: Auditable Agent Memory Under Change](https://arxiv.org/abs/2611.20927)
- Problem: memory systems are usually evaluated on fixed histories, but in practice facts change, sources differ in trustworthiness and users ask to be forgotten.
- Method: a language model proposes facts, and explicit rules decide which value is current, which source to trust and what to delete. Each fact records its source and validity period. LEDGER+EP adds retrieval of raw conversation turns and purges those turns on deletion.
- Result on a synthetic coding-agent workload: LEDGER+EP scores 94.3% on the dev set (5 seeds) and 91.1% on the held-out set (5 seeds). The strongest baseline, full replay, scores 82.1% and 83.3%. When a deletion request only describes the fact, no deleted value enters the evidence.
- Result on a 210-question LongMemEval subset: LEDGER+EP scores 74.8%, tied with full replay, using 1% of the context.
- Limits: the synthetic workload is self-built by the authors, and differences among the top systems on LongMemEval fall within the confidence intervals.

### [Stopping Is Not the Limit: Long-Horizon Vulnerability Exploitation](https://arxiv.org/abs/2611.22888)
- Problem: agents stop before the budget is used up. What happens if they keep going?
- Method: the authors find that a rising share of stop responses within the same context, and summaries containing "impossible" judgments, both correlate with inefficient continuation. They propose SCoRe, which compresses the context on consecutive stops and marks those judgments as "unconfirmed".
- Result: SCoRe beats summary-based continuation and other context-management baselines. MiMo reaches 67.0% capability coverage at 2,000 turns, against 32.4% under the original stopping policy. For comparison, GPT-5.5 scores 58.6% by the 300-turn ExploitBench reference.

### [When Agent Skills Go Stale: Runtime Behavior and Selective Maintenance](https://arxiv.org/abs/2611.22525)
- Problem: after the environment changes, some parts of a skill's state are stale and some are still useful.
- Finding (4 task settings, 2 models): a previously helpful skill can push task performance more than 10 percentage points below using no skill, or raise execution cost by nearly 40%.
- Method: selective maintenance. It replays checks from successful executions with no extra model calls, verifies whether differences conflict with the skill state, repairs and validates, and rebuilds if a local fix fails. It is not told what changed in the environment.
- Result: versus reusing the stale state, accuracy rises by up to 67pp and execution steps fall by up to 37%. Together with Experience Rot and the skill self-rewriting paper, this makes three angles on the same theme.

### [Beyond Plain MCP: Do Decision Models and Code Mode Make Tool Use Cheaper and Faster?](https://arxiv.org/abs/2611.19123)
- Problem: when an MCP gateway manages a large tool catalog, which works better: code mode or a decision layer (routing) in front?
- Method: a preregistered evaluation with 12 servers, up to 1,958 distractor tools and 3 open-source agents.
- Result: code mode saves 70–90% of tokens versus plain MCP and has clearly higher utility. Declaring the return structure in code-mode stub functions can swing a weak agent's success rate by up to 39.5 points, a bigger effect than adding routing. The hypothesis that "decision layer + code mode beats code mode alone" was not supported. The authors released the harness, a fine-tuned 4B tool-selection model and all evaluation traces.

### [Where Should LLM Agents Adapt at Test Time? In Context, in Weights, or Both](https://arxiv.org/abs/2611.19700)
- Problem: when an agent works repeatedly in the same environment, should experience stay in context, go into the weights, or both?
- Method: under a unified online protocol, the paper compares ICL, GRPO, SDPO and their combinations, 14 adaptation mechanisms plus a stateless baseline. It uses Qwen3.5-9B on 109 tasks across 4 environments (SWE-bench Verified, AppWorld, ScienceWorld, BIRD-Critic-SQLite).
- Result: the best ICL strategy lifts average success from 28.8% to 49.4%, the largest single gain. Adding GRPO on top gives the highest score, 51.6%. SDPO is mixed. In trajectory analysis, ICL reduces lookup and trial steps but often skips checking and verifying the current task; adding GRPO restores those behaviors.

- [HyperHarness: Learning to Generate Personalized Agent Harnesses from User Histories](https://arxiv.org/abs/2611.29062): learns a shared history-to-harness generator that produces a user's own retrieval and answer-guidance code in one pass from their history. It gets the top total score in 7 of 9 settings and uses 90.32% fewer tokens than long-context prompting at answer time.
- [FORGETMENOT: Auditing Memory Driven Privacy Risks in Commercial AI Agents](https://arxiv.org/abs/2611.29804): audits the long-term memory of 5 commercial AI agents over about 3800 sessions. - [Carried-Over and Agent-Native Threats in the Supply Chain of LLM Agent Skills](https://arxiv.org/abs/2611.30932): the first registry-level study of all 48,682 skills on ClawHub. Of skills with resolvable dependencies, 49.6% depend on versions with known CVEs, and 78.3% of those were already vulnerable at release. Agent input reaches the vulnerable function in only 3.0% of affected skills.
- [MORSE: Optimizing Streaming Memory Design via Open-World Auto-Research](https://arxiv.org/abs/2611.30011) (👍2): an editor classifies failures by cause, then retrieves papers, model cards and code to improve a streaming-video memory harness. On OVO-Bench, Qwen3-VL-8B reaches 75.1% accuracy at 0.30 seconds on average, 3.1 points ahead of the next-best harness.
- [What Makes Good Data for Training Coding Agents? A Systematic Study on SWE-Gym](https://arxiv.org/abs/2611.30207) (👍10; [Arist12/SWE-Gym-Verified](https://github.com/Arist12/SWE-Gym-Verified)): audits SWE-Gym's reward labels. On tasks a 9B baseline never solved, 74% of the tests reject a correct fix. Training on the audited tasks scores 2.4 and 2.7 points higher on SWE-bench Verified and Pro. It releases 1,087 audited tasks.

## 5. Research trend observations

- "Experience goes stale": Experience Rot, skill self-rewriting and skill staleness are all papers that just appeared on arXiv or HF with few upvotes. They agree that accumulated memory or skills can end up worse than having none after the environment changes. The fixes proposed are selective maintenance (the stale-skills paper) and marking expert knowledge the model can't write itself (SkillDiff).
- Memory and compression evaluation now looks at cost and reliability: LEDGER+EP uses 1% of the context, DMC-5 exploits compressor cache hits, CLAM builds memory 3–151× faster, and LiveLoRA migrates the KV cache. Papers report tokens, cache and latency alongside accuracy, not accuracy alone.
- Harness is a frequent word in the new batch (Section 4). The two most-upvoted harness papers are Embo-Harness (👍88) and AutoPILOT (👍30), both in embodied or game/real-time settings. Hot papers on pure Agent Context still have almost no HF upvotes, so the heat signal sits mainly in embodied work and model reports.
- Memory and skills are being treated as things to audit: HEAMS (memory-system evaluation), FORGETMENOT (commercial-agent memory privacy), the skill supply-chain and detector studies, and MCP tool-provider misbinding. The GitHub side was not checked online, so this point rests on paper data only and makes no claim about matching engineering projects.
