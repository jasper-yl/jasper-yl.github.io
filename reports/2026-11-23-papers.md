## 热度榜：Agent Context 精选

### [Continual-ARC: Measuring Skill Acquisition over a Working Lifetime](https://arxiv.org/abs/2611.14505)
- 热度：HF 👍3（入榜 7 天，首次出现时 9，现为 3，新增 -6）；X 提及 0；代码 [unifyai/continual-arc](https://github.com/unifyai/continual-arc) ⭐39，是今日 hot 里星数最高的。
- 问题：现有持续学习基准只看单一领域，每个实例只出现一次，也只比较一类学习器，记忆式和权重式系统很少放在同一尺度上比较。
- 方法：基于三个 ARC-AGI 版本构建终身任务流，同一任务隔一段时间带新实例回归，新任务不断加入。学习者可以花钱看示例、提交答案或在 harness 里行动，按消耗的反馈预算打分；流结束后冻结，分别测对见过任务的记忆和对未见任务的泛化。测试对象是权重冻结的 agent harness（带或不带持久化，用 Qwen3.5-9B 和 GLM-5.3 Flash），对照两个 prompting 下限、一个程序归纳方法，以及模仿 GLM-5.3 Flash 训练的 Qwen3.5-9B 权重。
- 结论/意义：harness 的持久化通常不提升记忆，除非有明确的专家指导；多数 harness 方法学到的比「只缓存每个任务示例」还少。没有任何 harness 方法在未见任务上有提升，权重学习则有明显提升。

### [Experience Rot: Experienced Agents Fail Where Novices Succeed](https://arxiv.org/abs/2611.20922)
- 热度：arXiv 来源，无 HF 点赞，heat=0，无代码仓库；入榜 6 天。
- 问题：agent 会保存对话历史、记忆文件、检索笔记和 skills 来复用经验，工具（MCP 定义）被悄悄改动后，这些经验反而可能害了它。
- 方法：用 MCP 定义的工具，在多种模型上测试工具静默变更，比较有经验的 agent 和没做过该任务的新手 agent。测了各种形式的记忆，也测了「通知更新」「指向文档」等补救办法。
- 结论/意义：变更后有经验的 agent 在多数任务上失败，新手大多成功；前者照抄之前的调用，不核对当前接口，还会报告成功。每一种被测的记忆形式都有此问题，且随经验量增加而加重。通知更新几乎没用，文档写得不清楚时指向文档也没用。

### [CarryOn: Learning What to Keep in Context for Long-Horizon LLM Agents](https://arxiv.org/abs/2611.17808)
- 热度：arXiv 来源，无 HF 点赞，heat=0；入榜 7 天。
- 问题：摘要会丢掉后续动作需要的精确细节，保留全部历史又带来大量无关信息。
- 方法：轻量上下文管理器，把紧凑的执行状态和带来源链接的细粒度证据配对，用学习到的选择器和自适应保留策略管理上下文，不额外调用 LLM。同时提出两个指标：S_α 优先看任务成功并兼顾资源消耗，NCS 衡量每次成功的归一化成本。
- 结论/意义：在 AppWorld、OfficeBench、Tau2 Telecom 上，三种 LLM Actor 的宏平均任务成功率为 75.7%，比最强基线高 6.7 个百分点，两个指标的平均分也最好。

### [LEDGER: Auditable Agent Memory Under Change](https://arxiv.org/abs/2611.20927)
- 热度：arXiv 来源，heat=0；入榜 6 天。
- 问题：现有记忆系统多在固定历史上评测，而现实里事实会变，来源可靠性不同，用户还会要求遗忘。
- 方法：语言模型只负责提出事实，哪个值是当前值、信任哪个来源、删除什么，由显式规则决定。每条事实保存来源和有效期。LEDGER+EP 另加对原始对话轮次的搜索，作为账本覆盖不到时的兜底，删除时也会清除这些轮次。
- 结论/意义：在作者自建的合成多会话 coding-agent 负载上，LEDGER+EP（fallback 模式）答对 94.3%（5 个开发种子）和 91.1%（5 个留出种子），最强基线全量回放为 82.1% 和 83.3%。在 LongMemEval 的 210 题子集上，augment 模式与全量回放准确率同为 74.8%，上下文只用 1%。局限：合成负载由作者自建，LongMemEval 上最强系统之间的差异落在置信区间内。

### [Instant Weight-Space Consolidation for Long-Term Memory in LLMs (CLAM)](https://arxiv.org/abs/2611.20759)
- 热度：arXiv 来源，heat=0；入榜 6 天。
- 问题：文本式 agent 记忆里模型本身不进化，抽取错误会累积，跨会话的隐含模式浮不出来，构建成本还随对话增长。
- 方法：循环超网络把一串会话激活一次前向编译成低秩 adapter，作为参数化记忆，不做梯度更新，也不调用语言模型生成。再配一个情景缓冲区，在推理时提供原文细节；带门控的潜状态跨会话传递，大小固定。
- 结论/意义：在 LoCoMo 和 LongMemEval-S、三个 2–7B 开源模型上，领先所有 agentic 基线 1–45 点，领先所有基于梯度的参数化方法 10–45 点，构建记忆比抽取式系统快 3–151 倍。缓冲区漏掉证据时 adapter 额外加 12–15 点，缓冲区是 oracle 时仍加 4–5 点。

### [Where Should LLM Agents Adapt at Test Time? In Context, in Weights, or Both](https://arxiv.org/abs/2611.19700)
- 热度：arXiv 来源，heat=0；入榜 6 天。
- 问题：agent 在同一环境里反复工作时，可以靠上下文里保留经验（ICL）或更新权重来适应，两者通常分开研究，各自的贡献和互补性不清楚。
- 方法：在共享在线协议下比较 ICL、GRPO（可验证奖励 RL）和 SDPO（自蒸馏）及其组合，共 14 种适应机制外加无状态基线。用 Qwen3.5-9B，在 SWE-bench Verified、AppWorld、ScienceWorld、BIRD-Critic-SQLite 四个环境的 109 个任务上测试，每个环境五种任务顺序。
- 结论/意义：ICL 单独带来的增益最大，最佳策略把平均成功率从 28.8% 提到 49.4%，再加 GRPO 最高到 51.6%，SDPO 效果不一。轨迹分析显示 ICL 常跳过对当前任务的检查和验证，GRPO 能帮助恢复这些行为。

### [Beyond Plain MCP: Do Decision Models and Code Mode Make Tool Use Cheaper and Faster?](https://arxiv.org/abs/2611.19123)
- 热度：arXiv 来源，heat=0；入榜 6 天。
- 问题：MCP 网关管理大量工具目录时，代码模式（agent 写脚本调用工具桩）和决策层（廉价路由器预选工具子集）哪种更好？
- 方法：预注册评测，12 个服务器、最多 1,958 个干扰工具，用 Qwen、Gemma、Nemotron 三个开源 agent，在封存的测试集上评估。公开了 harness、一个微调的 4B 工具选择模型和所有评测轨迹。
- 结论/意义：代码模式比普通 MCP 节省 70–90% token，效用也明显提升。在代码模式桩里声明返回结构提示是一阶变量，对较弱的 agent 可使成功率摆动最多 39.5 点，比加路由器的影响更大。「决策层加代码模式优于单独代码模式」这一核心假设没有被证实。

### [EfficientSkill: Learning Skills for Token-Efficient Multi-Turn Agents](https://arxiv.org/abs/2611.19823)
- 热度：arXiv 来源，heat=0；入榜 6 天。
- 问题：反思式 skill 优化器不断累积边角规则，提示膨胀，token 暴涨，agent 陷入冗长易错的循环。
- 方法：分两步。先在无 token 惩罚下找到可靠 skill，再从该 skill 热启动做带准确率保护的剪枝：压缩指令，限制轮数，把可复用代码转成零提示成本的工作区工具。
- 结论/意义：在 MATH-500、ALFWorld、SpreadsheetBench 上、四个模型中，12 个配置里有 11 个比不加约束的 EvoSkill 少输出 token（最多少 80%），每个基准的平均准确率都上升；SpreadsheetBench 上 Gemini 3.8 Flash 和 Grok 4.1 Fast 分别 +14.3 和 +17.5 个百分点。无论是否使用全前缀 KV cache，总 token 和服务成本在所有评测配置下都降低。

## 研究趋势观察

- 经验和记忆会过期，也会反噬。
  - [Experience Rot](https://arxiv.org/abs/2611.20922)（工具静默变更后带经验的 agent 失败）和 [Continual-ARC](https://arxiv.org/abs/2611.14505)（harness 持久化不如缓存示例，对未见任务无增益）都说明记忆不等于更强。
  - 相关的还有 [LEDGER](https://arxiv.org/abs/2611.20927) 对事实变化、可信来源和可删除性的规则化管理，以及 [2611.19264](https://arxiv.org/abs/2611.19264)、[2611.19859](https://arxiv.org/abs/2611.19859) 对更新后读一致性和依赖修复的研究。
  - 今天热度榜里，可靠性和治理类问题比单纯提点数的方法多。
- 上下文管理分两头。
  - 一头在 agent 侧做学习式选择与保留（[CarryOn](https://arxiv.org/abs/2611.17808)、[EfficientSkill](https://arxiv.org/abs/2611.19823)），另一头在推理服务层做 KV 与运行时驱逐（[Contexture](https://arxiv.org/abs/2611.26980)，针对 Hermes、OpenClaw、Codex 这类 harness 重发历史的问题）。
  - 两者都靠减少重发的历史来换成本和吞吐，也都强调不增加额外 LLM 调用。
- Harness 做强制执行，不让模型自己判断。
  - [SilentGuard](https://arxiv.org/abs/2611.20595) 的警告模式仍有 70.1% 错误，强制执行才见效；[Intent Contracts](https://arxiv.org/abs/2611.24025) 让规划者不持有工具；[Epistemic Guard](https://arxiv.org/abs/2611.27095) 做进程外回执。
  - MCP 工具元数据一侧，有 [GRAFT](https://arxiv.org/abs/2611.27041) 和 [2611.21577](https://arxiv.org/abs/2611.21577)（provider misbinding）的攻击研究。
  - 以上是论文层面的共同方向，今天没有核对 GitHub 项目侧的数据。
